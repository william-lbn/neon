## 1. 新发现：Grow 的 FATAL 清理改写另一操作（P1，已复现）

源码：PG `src/backend/storage/buffer/dsg_buffer_grow.c:111`、`:126`、`:291`，
以及 `src/backend/storage/ipc/ipc.c:238`。

`DsgGrowInterrupted()` 只检查共享的当前 phase 是否 PREPARING，便调用 DsgGrowDeny；
注册清理时传入0，没有携带本次 operation 身份。Deny 不仅发布 phase/reason，还修改
Granule 目录，而该目录约定由 resize_lock 串行保护。

FATAL 时，shmem_exit **先 LWLockReleaseAll，再执行 before_shmem_exit 回调**。
因此旧协调者的回调开始前，新协调者已经可能获得 resize_lock 并建立另一 PREPARING
操作。旧回调会把新操作当成自己的操作修改。这与普通 ERROR 在局部展开时仍持锁不同。

### 实际复现

使用已绑定的 c47f959 二进制和独立临时集群；评审模块仅利用已有注入点暂停真实
Grow/退出回调，不直接写 DSBCtrl、refcount、phase 或测试成功状态。

1. 操作1在真实 Grow 发布前发生 FATAL；退出探针在原生放锁后、原 Grow 清理前暂停。
2. 操作2取得真实 resize_lock，完成准备，在发布前暂停。
3. 恢复操作1的退出回调，操作2保持暂停；读取操作2事实。
4. 再恢复操作2，让其正常提交。

| 时刻 | 实际事实 |
|---|---|
| 操作2已持锁，发布前暂停 | `op=2 phase=1 reason=0 H=256`（PREPARING/NONE） |
| 操作1清理完成，操作2仍暂停 | `op=2 phase=3 reason=3 H=256`（错误 DENIED/INTERRUPTED） |
| 操作2正常返回 | `committed high=2048 generation=2 replay=false` |
| 最终共享状态 | `op=2 phase=2 reason=3 H=2048`（COMMITTED仍残留INTERRUPTED） |

这证明实际操作状态被错误归属、终态原因不一致；**没有复现数据损坏**，不将影响扩大
为已经发生错误回收。现有18项测试覆盖 IO/pin 的 FATAL，没有覆盖此 Grow/FATAL 交错。

评审复现源码、驱动、编译和输出保存在工作区 `build/audit-grow-fatal/`；先前探针因
注入点库名查找失败，修正为安装前缀中的短库名后成功复现，不把首次失败算作证据。

### 修复约束

清理必须绑定原 boot/revision/operation 身份，并在真实持有串行权且身份仍相符时才
修改共享操作。FATAL 的锁释放后路径单独处理；无法取得所有权时保留事实/预算并由
后续协调者对账，不能直接修改当前全局 operation。不能只把 reason 清零掩盖竞态，
也不应为了此模块改写 PG 通用退出顺序。修复后必须增加此确定性交错回归和相关完整检查。

## 2. 完整 Shrink 尚不存在（P0 交付阻断，功能缺失）

- 内核公开协调接口只有 DsgBufferGrow/GetSnapshot，没有生产 Shrink 协调器。
- `freelist.c:418` 的 StrategySetAllocationLimit 只改 L/过滤 freelist；其注释明确
  不降低 H、不回收 backing。它是排水前置栅栏，不是完整缩容。
- 当前 H 发布路径在初始化与 Grow；没有串起尾部 pin/IO/dirty 排水、tag/hash 撤销、
  最终 H 下降、逐数组物理回收、部分失败、取消、regrow 的生产路径。
- DsgRegionRelease/ReleaseTail 原语已经存在，但源码调用搜索只有测试使用；尚未由
  Buffer 缩容协调器调用。不能把独立 Provider 原语当作 Buffer Pool 已经能缩容。

所以还不能验收真实“扩→缩→扩”、Shrink 期间旧 ID/hash re-pin 和部分回收恢复。
这些逻辑及确定性并发测试中相当部分可以先在 Mac 实现，不应全部推迟到 Linux。

## 3. Neon 控制链尚未接入（P0 交付阻断，功能缺失）

对比本次官方 main，`compute_tools`、`libs/vm_monitor`、`pgxn/neon` 和
`pgxn/neon_test_utils` 目录没有本功能代码差异；Autoscaling 的 Agent、Controller 和
VM API 目录也没有 DSGA 业务差异。已有维护、构建/CI、WAL decoder/rmgr 变化不等于
DSGA 控制链实现。

| 组件/职责 | 现状 | 必须补齐 |
|---|---|---|
| Compute启动/内部恢复 | PG仍以启动NBuffers初始化；有boot更新测试 | 按最低VM规格计算B_boot、M及固定成本；覆盖同Postmaster恢复与新boot准入 |
| PG/Neon生产接口 | Grow由test_dsg_region测试函数调用，生产头文件注明尚无用户SQL入口 | capabilities/request_resize/status/cancel/memory_status，内部认证、范围、重放与独立receipt |
| Monitor | runner.rs:205仍主要管理filecache和cgroup观测阈值 | 驱动PG操作、执行预算/排空约束、处理新boot/重连/响应丢失、分类阻塞和跨层事实 |
| Agent/Scheduler | 沿用现有资源请求，未携带新PG/预算/许可身份 | 持久意图、预留、先VM增容再PG Grow、先安全排水再VM缩容及失败对账 |
| Controller/Runner/QMP | 既有VM伸缩能力仍在，未接入DSGA新协议 | VM UID/epoch/操作身份/条件执行、旧在途动作、迁移互斥和实际完成回执 |

Autoscaling `pkg/agent/runner.go:729` 的相关请求仍是replace CPU/memory/targetRevision，
没有这里所需的DSGA条件测试/许可身份；Monitor `runner.rs:245` 使用近期non_reclaimable
观测，`:288` 更新内部threshold，不能当作未来查询内存已受硬约束的证明。
这是现有链路尚未适配新协议的证据，不声称官方静态模式原本就必须满足本项目新协议。

## 5. 另两个具体缺口

### 扩展“清空全部缓存”语义未适配（P2）

`pgxn/neon_test_utils/neontest.c:249` 仍按启动 NBuffers 扫描。Grow 后 H>NBuffers 时，
它没有覆盖新增尾部，所以不能维持“扫描全部buffer”的语义。目前bootstrap下界保留
NBuffers，不将该点错误描述为已经证明越界或数据破坏；未来适配不能只换成H，仍须
引用保护与普通pin/IO协议。其他发行扩展也不能仅凭PG17版本号假设兼容。

### 仓库PR工作流未强制运行18项真实DSGA测试（P1验证缺口）

`.github/workflows/pull-request.yml:13` 运行Python unittest，但没有准备待测PG、两个
配套库及NEON_TEST_*环境。测试文件:23在缺少环境时显式skip。现有日志确为13项逻辑
通过/18项环境skip；18项本机另行执行通过，不能用PR绿色状态替代真实DSGA验证。
`ci/test-postgres.sh`也没有把上述真实集群套件接成DSGA验证门槛。
这不否定项目已有GitHub构建/发行CI；仅指出仓库内未看到这些专项测试被强制执行。
