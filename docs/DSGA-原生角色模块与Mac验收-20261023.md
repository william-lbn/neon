# DSGA 原生角色模块与 Mac 验收（2026-10-23）

本模块实现受管 Compute 的业务角色边界、主库原子应用、RO 回放核验和 SQL
认证目录保护；不是整个 V3 完成声明。默认关闭，不能据此开放公开创建或生产路由。
本页是本次角色模块的权威记录；旧收尾文档中的版本、计数是各阶段历史证据。

## 官方架构与最终约定

- PostgreSQL 实际源码仍在 Neon 的 `vendor/postgres-v17`；本批没有另建独立 PG，
  PG17 精确锁定 `9cf674a53bcadaef7b3faecacf61af3c1cf59aac`，三处版本一致。
- 官方 Compute 默认以 `cloud_admin` 通过内部管理通道连接；历史兼容回退创建
  该 SUPERUSER 时也没有 PG 口令。因此 `cluster.roles` 只容纳业务角色，内部
  管理身份不得使用租户口令，也不新增全局“私有管理 SCRAM”。外部管理 JWT/TLS
  与 PG 登录口令是不同的认证边界。
- 受管配置在 PGDATA 创建前拒绝内部/保留名、重复/超长名、MD5、非法 SCRAM、
  任意 SQL 选项和不声明角色的 JWT/数据库 owner。业务身份可无密码（如 JWT），
  有密码则必须是合法且有界的 SCRAM verifier。旧非受管模式保持原行为。
- 主库要求原始 `session_user`、当前身份均为 `cloud_admin` 且具备 SU/LOGIN。
  锁序固定为 `pg_authid` → `pg_auth_members`，在一个事务内检查完整成员图、
  清除遗留管理 PG 口令并应用角色。其他超级用户有口令则拒绝，交由受控迁移。
  **清除密码或 NOSUPERUSER 不会撤销已认证超级用户会话**；旧混用实例仍须
  受控重建/排空及来源验收，不能把本模块作为在线安全迁移证明。
- 原角色不补授 CREATEROLE/CREATEDB/弱组；改密沿用官方 LOGIN 默认，显式
  NOLOGIN 优先。发现原角色/弱组能到达 SU、内部管理或服务器文件/
  程序角色时拒绝，不静默降权。新普通 owner 保留 Neon 的默认兼容属性；JWT
  身份从同一已验证 spec 派生，默认不授予弱组/BYPASSRLS/CREATEROLE/REPLICATION。
  这些 owner 默认权限并不证明物理复制、后台维护和完整内存预算已经安全接齐。
- 参数化临时 SECURITY INVOKER 函数保证事务原子性，函数定义不含 verifier。
  提交前关闭私有会话的 SQL/参数/嵌套统计记录，错误仅返回 SQLSTATE；Role 的
  Debug 脱敏，JSON 协议不变。网络等待不持 Rust ctx 锁，提交及完整权威重读成功
  后才替换缓存；超时/断线/未知提交结果一律失败并要求对账。
- RO 不运行角色 DDL，使用独立管理连接，在单个 MVCC 快照核验真实 recovery、
  内部无 PG 口令、成员图/显式属性和源 timeline 已冻结业务 verifier；不重生成
  盐值或用主库成功冒充副本已经回放。启动与重配均接入该检查。
- 受管 local_proxy 配置延后到角色应用/核验成功后；文件写入/SIGHUP 失败阻止
  就绪。SIGHUP 成功不是代理已 reload 的回执，公开路由仍需独立来源/版本证明。

## SQL 认证目录防护的边界

Neon 真实弱组继承 `pg_read_all_data`、`pg_write_all_data` 与 `pg_monitor`，
仅 NOSUPERUSER 并不能保护 `pg_authid`。本次真实生产组测试曾复现越权读取，
失败日志保留，随后在 `pgxn/neon/dsg_control.c` 增加 PG17/API6、DSGA 开启时的
ExecutorCheckPerms 链式 hook：拒绝非原始管理 SU 会话读取密码列/整行、经
pg_shadow/SQL SECURITY DEFINER 绕过，以及 SQL 执行器直接写认证目录；保留
pg_roles 掩码和普通元数据。正常 ALTER ROLE 仍由 PG 原生 utility 权限检查负责。

这不是物理复制/WAL/备份、统计信息、任意不安全扩展或 HBA 的全通道证明；
内部管理无 PG 口令也不能代替私有网络/代理隔离。后续必须补齐物理复制命令边界、
Renderer、HBA、原始 Operation/VM/Config/boot 绑定的初始化回执和混合镜像正向
能力证明，之后才能批准公开接流。当前不关闭 V3 R02/R03。

## Mac 复验入口

使用 Xcode SDK 14.4、Rust 1.88、已安装的准确 Neon PG17，以及仓库锁定 Go
工具链；先核对 `postgres --version` 和三处版本锁，再运行：

```sh
python3 ci/compute.py validate --source-ref index --require-pg-checkout v17
bash ci/test-dsg-neon-extension.sh /实际PG构建目录 /实际PG安装目录
bash ci/test-dsg-managed-roles.sh /实际PG安装目录
bash ci/test-dsg-rust-client.sh /实际PG安装目录
bash ci/test-dsg-go-client.sh /实际PG安装目录 /自有autoscaling源码目录
python3 ci/test_dsg_creation_plan.py /自有control-plane源码目录 --report-dir /新的证据目录
```

每个严格门禁检查真实用例数量，拒绝零用例、ignored/skip/filtered 伪通过。
原生夹具使用新建 0700 私有目录/socket，实际创建主库与物理备库，不接触已有库。
共享夹具只新增带独立原始登录身份的连接和真实 pg_basebackup，不以 SET ROLE
冒充另一个 `session_user` 或只读 GUC 冒充备库。失败保留独占目录和日志。

本批最终测试数量、日志摘要、源码 SHA256 和自有远程发布身份见
[机器验收摘要](acceptance/dsga-managed-roles-mac-20261023.json)。候选和最终
提交分开记录；所有默认 ignored 原生用例另行显式执行，不计为默认 cargo 已执行。
