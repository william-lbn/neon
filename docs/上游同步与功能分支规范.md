# 上游同步、功能开发与合并规范

日期：2026-10-19。以下顺序来自项目所有者的明确要求，适用于 Neon、Autoscaling、
PostgreSQL fork 和后续各组件。业务开发不能绕过基线同步与验证。

## 必须遵守的顺序

1. 从你们的 `william-lbn/*` fork 获取代码；官方仓库作为只读 upstream。
2. 拉取最新官方默认分支及该组件实际使用的维护分支。比较完整提交祖先关系，
   保留自有 CI/发行改动，合入全部相关官方提交，不仅挑选几个标为 bug 的提交。
3. 如需处理冲突，在独立的 `codex/upstream-组件-日期` 分支合并、中文记录语义
   处理、完成构建及受影响模块全量验证。不能以“无文本冲突”代替正确性验证。
4. 从已核对/验证的最新基线建立独立业务分支，小批修改、关键逻辑详细中文注释，
   Mac 本地业务验证通过后模块化提交。原先实验改动迁移时保留来源与内容一致性证据。
5. 先推送你们 fork 的依赖分支，再推引用这些提交的主仓功能分支。gitlink、
   `ci/distribution.json`、`vendor/revisions.json` 和镜像来源必须一致。
6. 远程功能分支供 CI、集成、环境和性能验收。**全部必要测试通过并由你们确认后，
   才能将通过的功能合入你们自己的主分支。** 开发过程中不自动合并主分支，不发布生产。

“最新”是每轮核对时的官方公开提交。没有人能保证未知 bug 已全部修复。新上游
提交到来后按同样顺序重新同步和验证，不能直接用 `submodule update --remote`
覆盖带有自有功能的内核提交。

## 提交前的版本绑定验证

```sh
git add vendor/postgres-v17 ci/distribution.json vendor/revisions.json
python3 ci/compute.py validate --source-ref index --require-pg-checkout v17
python3 -m unittest discover -s ci -p 'test_*.py' -v
```

CI 默认检查已提交 HEAD；本地 `--source-ref index` 检查将要提交的内容。需要
实际构建时还检查指定版本已初始化、检出 SHA 匹配且无未提交源码，防止误编译
另一个目录的 PG。真实 PG 生命周期测试需显式提供待测二进制和配套测试库，CI
prepare 阶段没有这些环境时会显示 skipped，不能记作实际业务测试通过。
